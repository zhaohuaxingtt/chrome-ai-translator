## 调试：message channel closed → 分批发送修复

配置修对后又报 `A listener indicated an asynchronous response by returning true, but the message channel closed before a response was received`。

**根因：** 161 个段落块塞在一条 sendMessage 里，background 要等全部 161 次 AI 调用（4 并发，约 1-2 分钟）才回一次包；MV3 service worker 空闲约 30 秒会被 Chrome 回收，worker 被杀 → 通道关闭 → 整页翻译夭折。

**修复（translate-page.ts）：** 按批次（BATCH_SIZE=8）分多条消息发送，每批几秒内返回并立即渲染；每批消息重置 SW 存活计时；单批失败（try/catch）只损失该批不中断整页。新增 2 条测试（分批、单批容错），66 tests 全绿。

## 渲染方式重大修正：替换式 → 追加式（用户明确要求）

用户反馈「翻译把整个页面破坏了」。**根因**：原 `renderBilingual` 用 `element.textContent = ''` 清空容器再塞「译文+原文」两个 span——这会摧毁原站点的 HTML 结构与样式（链接、内联标签、布局全丢），且原文被弱化改写，等于改变了原布局。

**用户明确要求：不改变原有网站布局，在原有文字下方显示翻译。**

改造（66 tests 全绿）：
- `TextBlock` 新增 `nodes: Text[]`（该块所含文本节点），供渲染定位插入点。
- 渲染器改为 `renderTranslation(block, translated)`：**不清空任何东西**，只在最后一个文本节点后 `anchor.after(target)` 插入一个 `display:block` 的译文 span。原文节点、内联标签、样式全部原样保留。
- 幂等 = 先移除本块旧译文再插入；标记仍打在容器元素上供提取器跳过；`revertTranslation` 只移除译文节点。
- 不再需要 `data-ai-original`（原文从未被改写，回退无需还原）。

**教训：** 处理第三方页面时，「只追加、不改写」是铁律。任何 `innerHTML/textContent = ''` 式的替换都会破坏宿主页面。

## 完成 ticket 09：实时监听 + 译文自愈（71 tests 全绿）

用户反馈「翻译出现了一下又没了」——延迟只能躲过初次水合，躲不过 React 之后任意时刻的 re-render（重绘会抹掉我们插入的译文）。

## 调试：自愈没生效 → observer 挂载时序错误（已修复）

用户反馈译文仍「闪一下就没」。日志：成功 175 块失败 0，但**无任何重检日志**——自愈从未触发。

2. 每次 runTranslate 动态取当前 `document.body`。
3. 加重入保护（running/pending 标志）：监听器触发的重翻与进行中的翻译互斥，跑完补一轮。
4. onMutations 打日志「检测到页面变化」，便于下次诊断。

## 调试：日志全无 → waitForWindowLoad 无限等待的 bug

用户反馈「配置没问题但还是报错」，且 console **一条我们的日志都没有**（截图里的 recordedTabId / getAllPromptList 报错来自**别的扩展**，非本项目）。

**根因（真 bug）：** `waitForWindowLoad()` 不设超时，只有 `load` 事件触发才开始翻译。慢资源（图片/字体/埋点）会让 load 拖很久甚至不触发 → 翻译永不开始、页面毫无动静、无任何日志。

**排查技巧：** 先看探针日志是否存在 → 判断问题在注入层还是翻译逻辑层。

## 定位真因：自检条件 `=== 0` 过严（Elements 面板实证）

用户 F12 Elements 搜 `ai-tr-target` 只有 **2 个**（非 175），而容器上 `data-ai-translated="true"` 与 `data-ai-block-id="block-175"` **仍在**，且 `display:block !important` 已生效。

**修复（content/index.ts）：** 自检判据改为 `staleCount > 0 || alive < lastRenderedCount`（`countStaleTranslatedBlocks()` 复用「有标记但 querySelector 找不到译文」的 stale 判断），间隔 5s → **3s**，日志输出「检测到译文缺失（现存 X / 已渲染 Y），自动补翻」。

## 修复：Extension context invalidated 刷屏

## 根因修复：块级「已翻译」判断不精确（自愈失效的真因）

现象演进：自检已触发（`检测到译文缺失（现存 2 / 已渲染 198），自动补翻`），但**补翻后无「提取到 N 块」日志** → `translatePage` 提取到 **0 块** → 自愈形同虚设。

**真因：** 跳过逻辑有两处语义过宽：
1. `isSkipped` **沿祖先链**判定：任意祖先带 `data-ai-translated` 就跳过整棵子树。
2. stale 判断用 `container.querySelector('.ai-tr-target')`——只要**子树任意位置**残留一个译文，就认为「该块已翻译」。

而 Elements 面板显示存在 `block-175` 这种**包裹大量内容的大 div**：React 抹掉绝大多数译文后恰好还剩 2 个落在它子树里 → 该大容器被判为已翻译 → **它覆盖的 196 个块全部被跳过** → 提取 0 块。

**修复（精确到块）：**
1. 译文节点新增 `data-ai-target="<blockId>"`（`TARGET_FOR_ATTR`，见 `shared/translated-mark.ts`），标明这份译文属于哪个块。
2. extractor 导出 `isBlockTranslated(container)`：要求「有标记」**且**「存在属于它自己的译文」（`querySelector('.<TARGET_CLASS>[data-ai-target="<id>"]')`）。
3. `isSkipped` 拆为 `isInSkippedTag`（只判 SKIP_TAGS）；跳过判定移到主循环，只针对**文本节点所属的那个容器**：`if (container !== null && !isBlockTranslated(container))`。
4. content 自检的 `countStaleTranslatedBlocks` 复用 `isBlockTranslated`。

**教训：** 「某块已翻译」必须精确到该块自身，任何基于「子树里有没有」的判断都会在大容器场景下失灵。73 tests 全绿（extractor 测试改为用 `renderTranslation` 真实渲染后再验证跳过）。
